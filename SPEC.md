# SPEC — Модуль безопасности персональных данных

Техническая спецификация реализации. Главный документ проекта. Источник истины — ТЗ (`docs/task.txt`) и правила `AGENTS.md`. Расхождение с ТЗ выносится в `WORKLOG.md`.

---

## 1. Постановка задачи и требования

### 1.1. Задача
Разработать сервис-прокси между системой-потребителем и LLM, который:
- идентифицирует персональные данные (ПД) в тексте;
- маскирует их;
- демаскирует по `payload_id`.

Сервис оценивается внешней проверяющей системой AlfaSonar по контракту `POST /process`.

### 1.2. Функциональные требования (из ТЗ §4)
Идентифицировать и маскировать типы ПД:
- ФИО, дата рождения, место рождения, серия и номер паспорта, гражданство, орган выдачи паспорта, код подразделения, дата выдачи паспорта, серия и номер водительского удостоверения, адрес (страна, индекс, город, улица, дом, квартира), email, номер телефона, ИНН, номер платёжной карты, CVV, пин-код, имя держателя карты.

Требования:
- механизм определения принадлежности к ПД (Пушкин — не ПД, адрес отделения Банка — не ПД);
- расширяемость списка типов;
- независимость от регистра;
- логирование выявленных типов по каждому запросу;
- вариации написания (регистр, порядок дат, даты текстом, разделяющие слова);
- демаскирование с сохранением местоположения знаков;
- гибкая настройка по системам;
- качество ≥ 95%;
- обработка до 100 000 токенов.

### 1.3. Нефункциональные требования (из ТЗ §5)
- Безопасность: защищённый контур, шифрование, минимизация данных, никаких утечек.
- Надёжность: корректная обработка ошибок, деградация, понятные сообщения.
- Производительность: Latency ≤ 1 с, RPS = 1000.
- Масштабируемость: добавление типов ПД и рост RPS без роста Latency.

### 1.4. Дополнительные плюсы (из ТЗ §6, необязательно)
- Токенизация/детокенизация или замена синтетическими данными.
- Гибкая настройка вида маскирования по системе.
- RPS 2000 при Latency ≤ 1 с.
- Идентификация документов кроме паспорта РФ.
- Маскирование только при нескольких типах ПД (настраиваемо).

## 2. Контракт API и ограничения проверяющей системы

### 2.1. Контракт `POST /process`
```
POST /process
Content-Type: application/json
{ "payload": "<строка>", "payload_id": "<идентификатор>" }
→ 200
{ "result": "<строка>" }
```

Схемы (pydantic):
```
ProcessRequest:
  payload: str        # исходный текст (прямой шаг) или маска (обратный шаг)
  payload_id: str     # ключ корреляции маскирование→демаскирование
ProcessResponse:
  result: str
```

### 2.2. Ограничения проверяющей системы (из ТЗ Приложение A, B)

| Параметр | Значение | Источник |
|---|---|---|
| Тело запроса | только `{payload, payload_id}` | ТЗ Прил. A |
| Заголовки | нет (нет `X-System-Id`, нет ключей) | ТЗ Прил. A |
| Таймаут запроса | 10 с (дольше = неответ) | ТЗ Прил. B |
| Ретраи | до 2 на запрос (итого до 3 попыток) | ТЗ Прил. B |
| Стоп прогона | 5 невалидных ответов подряд | ТЗ Прил. B |
| 429 | допустим, не невалиден, не сбрасывает счётчик | ТЗ Прил. B |
| Нагрузка | ~5 мин, целевой RPS 1000 | ТЗ Прил. B |
| Latency | ≤ 1 с (ориентир) | ТЗ Прил. B |
| Объём текста | до 100 000 токенов | ТЗ §4.4 |
| Качество | ≥ 95% | ТЗ §4.4 |
| Протокол | http или https (self-signed, ssl_verify=false) | ТЗ Прил. B |

### 2.3. Правила, нарушение которых обнуляет результат (из AGENTS.md)
1. `/process` никогда не отдаёт 4XX/5XX. Любое исключение → исходный `payload` с кодом 200. Исключения: 422 от pydantic на нарушение схемы, 429 под перегрузкой с заголовком `Retry-After`.
2. `/process` не авторизует. Нет `X-System-Id` → `default_system`. 403 не возвращается.
3. Неизвестный `payload_id` — не ошибка. Обрабатывается как новый текст, 200. Никаких 404.
4. Роутинг из трёх веток (см. §3.1).
5. `--workers 1`.
6. Маска сохраняет длину и структуру.
7. Замена спанов — справа налево.
8. Значения ПД не попадают в логи.

## 3. Решения, определяющие архитектуру

### 3.1. Роутинг из трёх веток по id И payload
**Решение.** Направление определяется по `payload_id` и `payload`:
- id известен и `payload == mask` → вернуть `original` (демаскирование);
- id известен и `payload == original` → вернуть сохранённую `mask` (ретрай маскирования);
- id неизвестен → маскировать и сохранить.

**Почему.** Проверяющая система делает ретраи (до 3 попыток) с тем же id и тем же исходным текстом. Роутинг по одному только id не различает ретрай маскирования и обратный шаг: ретрай вернул бы `original` вместо `mask`, и прямой шаг провалился бы. Сравнение `payload` с сохранёнными `mask`/`original` различает эти случаи.

**Отвергнуто.** Роутинг по одному `payload_id` (id есть → демаскирование). Цена: ретрай прямого шага возвращает исходник вместо маски, метрика прямого шага обнуляется.

### 3.2. `/process` никогда не отдаёт 4XX/5XX
**Решение.** Любое исключение в обработке ловится и возвращает исходный `payload` с кодом 200. Исключения: 422 от pydantic (нарушение схемы), 429 под перегрузкой с `Retry-After`.

**Почему.** Проверяющая система останавливает прогон после 5 невалидных ответов подряд. 4XX/5XX (кроме 429) — невалидные ответы. Возврат `payload` как есть с 200 гарантирует, что прогон не остановится из-за внутренней ошибки.

**Отвергнуто.** 404 на неизвестный `payload_id`, 500 как штатный ответ, 403 на авторизацию. Цена: 5 таких ответов подряд останавливают прогон.

### 3.3. Vault (in-memory LRU с TTL) + `--workers 1`
**Решение.** Соответствия `payload_id → {mask, original}` хранятся в in-memory LRU-кэше с TTL. Сервис запускается строго с `--workers 1`.

**Почему.** Демаскирование идёт через vault по `payload_id`. При нескольких воркерах Store живёт в памяти каждого процесса отдельно, и демаскирование может попасть на воркер без записи. Один воркер + async достаточно для RPS 1000 (ТЗ §5). LRU ~500k записей, TTL ~час покрывает прогон ~5 минут.

**Ёмкость vs нагрузка.** Прогон ~5 мин (300 с) при RPS 1000 даёт до 300 000 записей (по одной на каждый запрос маскирования при уникальных id). Ёмкость 500 000 — достаточна, вытеснение не сработает. TTL 3600 с > 300 с — записи не истекают. При RPS 2000 (доп. плюс ТЗ §6) накопится до 600 000 записей > 500 000 — вытеснение сработает, часть демаскирований провалится. Ёмкость 500k рассчитана на целевой RPS 1000.

**Отвергнуто.** `--workers 4` (Store не общий, демаскирование ломается). Redis (внешняя зависимость, недоступность компонента нарушает требование деградации).

### 3.4. Маска сохраняет длину и структуру
**Решение.** Значащие символы → `*`, разделители остаются на местах. Длина маски равна длине исходного спана.

**Почему.** Метрика проверяющей системы — нормированный span-based Левенштейн между маской и эталонной маской. Сохранение длины и структуры минимизирует расстояние. Длина нужна для метрики, а не для демаскирования (демаскирование идёт через vault).

**Отвергнуто.** Плейсхолдеры вида `[TYPE_N]` (меняют длину, ломают метрику). Таблица масок без сохранения длины (увеличивает Левенштейн).

### 3.5. Качество = F1 по спанам против разметки генератора
**Решение.** Качество меряется F1 по спанам против разметки генератора, отдельно по каждому типу, плюс доля негативных примеров с ложными срабатываниями. Цель — 0.95 в строгом режиме.

**Почему.** Метрика должна сравнивать результат кода с независимым эталоном. Разметка генератора пишется в момент подстановки значения, а не парсингом готового текста — это независимый эталон.

**Отвергнуто.** Левенштейн против собственной маски на своём стенде (меряет строку против себя, всегда 1.0, не измеряет ничего).

## 4. Архитектура

### 4.1. Слои
```
HTTP (uvicorn, --workers 1)
  └─ app/api/          # эндпоинты: /process, /health, /ready, /metrics, /stats
       └─ app/core/    # pipeline (оркестрация), span, vault-интерфейс
            └─ app/detectors/   # детекторы ПД (по одному файлу на тип)
                 └─ app/masking/ # маскирование спанов
```

### 4.2. Поток обработки `POST /process`
1. pydantic валидирует `{payload, payload_id}`. Нарушение схемы → 422.
2. Pipeline: роутинг из трёх веток (§3.1).
   - id известен + `payload == mask` → вернуть `original`.
   - id известен + `payload == original` → вернуть `mask`.
   - id неизвестен → детекция → маскирование → сохранить в vault → вернуть `mask`.
3. Любое исключение → вернуть исходный `payload` с 200.

### 4.3. Структура модулей (из AGENTS.md §4)
```
app/
├── main.py                 # точка входа, uvicorn

├── vault/

│   └── memory.py           # in-memory LRU с TTL
├── detectors/

```

## 5. Модель данных

### 5.1. Span
```
Span:
  type: str          # тип ПД, например "passport"
  start: int         # позиция начала в оригинале
  end: int           # позиция конца (не включительно)
  value: str         # исходное значение (только внутри обработки, не в логи)
  confidence: float  # уверенность [0..1]
```

### 5.2. MaskRecord (запись vault)
```
MaskRecord:
  payload_id: str
  mask: str          # замаскированная строка
  original: str      # исходная строка
  types: list[str]   # выявленные типы ПД
  created_at: float  # timestamp для TTL
```

### 5.3. Vault-интерфейс
```
class Vault(ABC):
    def get(self, payload_id: str) -> MaskRecord | None
    def put(self, record: MaskRecord) -> None
    def stats(self) -> dict
```

## 6. Предметная логика

### 6.1. Детекция
- Каждый тип ПД — отдельный файл в `app/detectors/`, базовый класс, саморегистрация при импорте, каталог сканируется при старте.
- Вызов каждого детектора обёрнут в `try-except`: падение одного не роняет запрос.
- Контрольные суммы обязательны: Луна для карт, контрольные разряды для ИНН, контрольное число для СНИЛС.
- ИНН: 12 цифр — физлицо (маскируем), 10 цифр — юрлицо (не ПД).
- Якорные слова обязательны для CVV, пин-кода, кода подразделения, в/у. Якорь и co-occurrence — разные настраиваемые правила.
- ФИО: якорь перед ФИО не требуется; контекст (поэт, писатель, памятник, музей) — негативный признак. Морфология суффиксов, не словарь фамилий.
- Адрес — один составной спан от первого до последнего компонента. Топонимы из двух слов и с дефисом обязательны.
- Регистронезависимость — флагом `re.IGNORECASE`, не нормализацией текста.
- Никаких вложенных квантификаторов в regex (катастрофический откат). Лечится переписыванием паттерна, не таймаутом.

### 6.2. Резолвер пересечений
Между детекцией и маскированием — резолвер пересечений: приоритет типа → длина спана → уверенность. Типам с контрольной суммой приоритет выше.

### 6.3. Маскирование
- Замена спанов — справа налево (иначе смещения едут после первой замены другой длины).
- Значащие символы → `*`, разделители остаются на местах.

### 6.4. Демаскирование
- По `payload_id` из vault возвращается `original`.

---

## 7. Разрешение конфликтов между частями

- **Пересечение спанов разных детекторов**: резолвер (§6.2) выбирает по приоритету типа → длине → уверенности. Типы с контрольной суммой выше.
- **Ретрай vs обратный шаг**: роутинг из трёх веток (§3.1) различает по `payload` (mask vs original).
- **Падение одного детектора**: `try-except` вокруг каждого, остальные работают.
- **Неизвестный id**: обрабатывается как новый текст (200), не ошибка.

## 12. Инструменты разработки

### 12.1. Генерация тестовых данных
- `python tools/gen_dataset.py` — генератор синтетических данных.
- Смещения спанов генератор пишет **в момент подстановки значения**, не парсингом готового текста. Это независимый эталон.

### 12.2. Измерение качества
- `python tools/score.py` — скорер.
- Метрика: **F1 по спанам против разметки генератора**, отдельно по каждому типу, плюс доля негативных примеров с ложными срабатываниями. Цель — 0.95 в строгом режиме.
- **Совпадение спана** — точное совпадение границ `[start:end]` с эталоном. Сдвиг границы на 1 символ даёт F1 = 0.0 по типу (спан не засчитывается). Это объясняет строгость цели 0.95: нужна точная детекция границ, а не приблизительная.
- **Левенштейн против собственной маски не применять** — он меряет строку против себя и всегда даёт 1.0.

### 12.3. Исключение подгонки
- Holdout-датасет с другим seed в отладке не используется.
- Заявлять «готово» без запуска скорера нельзя.

## 13. Критерии готовности

Проверяемые запуском утверждения. Все критерии проверяются командой `qa` (запуском тестов, скорера, нагрузочного теста, проверкой логов); `impl` отвечает за их выполнение.

| # | Критерий | Команда |
|---|---|---|
| 1 | Запустить `pytest` → все тесты контракта проходят | qa |
| 2 | Отправить `POST /process` с новым id и исходным текстом → вернётся `{"result": "маска"}` | qa |
| 3 | Отправить `POST /process` с тем же id и тем же исходным текстом (ретрай) → вернётся та же `маска` | qa |
| 4 | Отправить `POST /process` с тем же id и маской → вернётся `original` | qa |
| 5 | Отправить `POST /process` с неизвестным id → вернётся 200 (не 404) | qa |
| 6 | Отправить `POST /process` с невалидным JSON → вернётся 422 (не 500) | qa |
| 7 | Запустить `python tools/score.py` → F1 ≥ 0.95 по каждому типу, доля ложных срабатываний на негативных примерах ≤ 0.05 | qa |
| 8 | Запустить сервис с `--workers 1` → работает | qa |
| 9 | Прогнать нагрузочный тест → RPS ≥ 1000, Latency p95 ≤ 1 с, нет устойчивого 429 | qa |
| 10 | Проверить логи → значения ПД отсутствуют | qa |

## 14. Известные ловушки

1. **Вложенные квантификаторы** `(?:\d[ -]?){13,19}` → катастрофический откат на длинном тексте, запрос зависает > 10 с → неответ → стоп прогона. Лечится переписыванием паттерна.
2. **Замена спанов слева направо** → после первой замены другой длины смещения едут, последующие спаны маскируются неверно. Только справа налево.
3. **Нормализация текста для регистронезависимости** → спаны нормализованной строки не приложатся к оригиналу, маскирование ломается. Только `re.IGNORECASE`.
4. **Роутинг по одному id** → ретрай прямого шага возвращает `original` вместо `mask`, метрика прямого шага обнуляется.
5. **`--workers > 1`** → Store не общий, демаскирование попадает на воркер без записи → возврат payload как есть → обратный шаг провален.
6. **404 на неизвестный id** → 5 подряд останавливают прогон.
7. **Логирование значений ПД** → утечка, нарушение требования безопасности.
8. **Повторный прогон детекторов ради лога** → лишняя нагрузка и риск рассинхрона спанов.
9. **Словарь фамилий** → неполнота (редкие фамилии) и ложные срабатывания (частотные слова). Только морфология суффиксов.
10. **Плейсхолдеры `[TYPE_N]`** → меняют длину, ломают метрику Левенштейна.

## Вопросы, на которые ТЗ не отвечает, и трактовки

1. **Что такое «токен» в «100 000 токенов»?** ТЗ не определяет. Трактовка: токен ≈ слово; лимит на длину payload в символах (например, 1 млн символов), проверяется на предельных данных.

2. **Как именно считается «качество 95%»?** ТЗ не определяет метрику. Трактовка (из AGENTS.md): F1 по спанам против разметки генератора, отдельно по каждому типу, плюс доля негативных примеров с ложными срабатываниями.

3. **Как различать ретрай маскирования и обратный шаг?** ТЗ говорит «по payload_id», но ретраи шлют тот же id с тем же текстом. Трактовка: роутинг по id И payload (три ветки).

4. **Что делать с неизвестным payload_id?** ТЗ не говорит. Трактовка: обрабатывать как новый текст, 200 (не 404), чтобы не останавливать прогон.

5. **Как проверяющая система идентифицирует систему-потребителя?** ТЗ требует ограниченный список систем, но проверяющая не шлёт заголовок. Трактовка: на `/process` применяется `default_system`.

6. **Что такое «сохранение местоположения знаков» при демаскировании?** ТЗ требует. Трактовка: маска сохраняет длину и структуру (для метрики Левенштейна), а демаскирование идёт через vault по payload_id.

7. **Какие именно «сложные предложения» в датасете?** ТЗ упоминает, но не определяет. Трактовка: предложения с несколькими типами ПД и контекстом, включая негативные примеры (Пушкин, адрес Банка).
