# Модуль безопасности персональных данных — Извлечённые цели, ограничения, задачи и критерии

Извлечено из ТЗ трека (документ «Модуль безопасности персональных данных — ТЗ трека»).

---

## 1. Цели

1. Разработать **Модуль безопасности персональных данных** — сервис-прокси между системой-потребителем и LLM.
2. Обеспечить **идентификацию** типов персональных данных (ПД), их **маскирование** и последующее **демаскирование**.
3. Выдерживать **нагрузку обращений к LLM**, отвечать **быстро и качественно**.
4. Соблюдать **безопасность и приватность** персональных данных при обращении к LLM (требования Банка, законодательство РФ, нормативная база, требования ЦБ).
5. Создать **переиспользуемое** решение, устраняющее разрозненность решений разных команд.
6. Обеспечить **гибкость настройки** правил маскирования для разных типов ПД и разных систем-потребителей.
7. Обеспечить **отказоустойчивость** и **масштабируемость** сервиса.
8. Реализовать **контракт API** `POST /process` для автоматической проверки (маскирование и демаскирование, коррелируемые по `payload_id`).

## 2. Ограничения

### 2.1. Функциональные ограничения
- Обязательное покрытие всех перечисленных типов ПД (см. раздел «Задачи»).
- Идентификация не должна зависеть от регистра.
- Учёт разных вариаций написания ПД (регистр, порядок дат, даты текстом, разделяющие слова).
- Демаскирование с сохранением местоположения знаков.
- Обработка крупных массивов текста — **до 100 000 токенов**.
- Качество идентификации/маскирования/демаскирования — **не ниже 95%**.
- Механизм определения принадлежности данных именно к персональным (например, «Александр Пушкин» — не ПД; адрес отделения Банка — не ПД).
- Возможность расширения списка идентифицируемых ПД.

### 2.2. Нефункциональные ограничения
- **Безопасность**: обработка в защищённом контуре, соответствие стандартам ИБ банка; никаких утечек, шифрование, минимизация данных; исходные защищаемые данные не должны попадать в логи и технические метрики.
- **Надёжность**: корректная обработка ошибок API, деградация функционала при недоступности сервисов, понятные сообщения пользователю.
- **Производительность**: Latency — **не более 1 секунды**, RPS — **1000**.
- **Масштабируемость**: добавление настроек для новых типов ПД и рост RPS без роста Latency.
- **SLA**: скорость, доступность, стабильность.

### 2.3. Ограничения упаковки решения (проверка качества кода)
- Только **zip-файл** с исходным кодом.
- Не включать: датасеты, дампы, архивы, медиа, скомпилированные бинарники.
- Не включать каталоги зависимостей и сборки: `node_modules`, `.venv`, `venv`, `env`, `target`, `build`, `dist`, `out`, `bin`, `obj`, `.git`, `.idea`, `__pycache__`, `coverage`.
- Разумный размер архива; исходный код в корне или в понятной структуре.

### 2.4. Ограничения нагрузочного тестирования
- Таймаут одного запроса — **10 секунд** (дольше = неответ).
- Ретраи — **до 2** на запрос (итого до 3 попыток); эндпоинт должен быть **идемпотентным** по `payload_id`.
- **429** допустим под нагрузкой (учитывается `Retry-After`); устойчивый 429 — значимый результат (решение не держит нагрузку).
- **Стоп** при 5 невалидных запросах подряд (429 невалидным не считается и счётчик не сбрасывает; успешный ответ сбрасывает счётчик).
- Нагрузка: ~5 минут, целевой RPS 1000; элементы датасета переиспользуются.
- Целевой Latency — не более 1 с (ориентир, не жёсткий лимит).
- Развёртывание на http или https (самоподписанный сертификат допускается; проверка с `ssl_verify=false`).

## 3. Задачи

### 3.1. Идентификация типов ПД
Однозначно идентифицировать:
- ФИО
- Дата рождения
- Место рождения
- Серия и номер паспорта
- Гражданство
- Орган, выдавший паспорт
- Код подразделения
- Дата выдачи паспорта
- Серия и номер водительского удостоверения
- Адрес (в т.ч. отдельно: страна, индекс, город, улица, дом, квартира и т.п.)
- Email
- Номер телефона
- ИНН
- Номер платёжной банковской карты
- CVV-код
- Пин-код карты
- Имя держателя карты

Дополнительно:
- Механизм определения принадлежности данных к персональным (исключение ложных срабатываний).
- Расширяемость списка идентифицируемых ПД.
- Независимость от регистра.
- Логирование выявленных типов ПД по каждому запросу.

### 3.2. Маскирование
- Учёт вариаций написания: регистр; разное расположение года/месяца/даты (мм.дд.гггг, гггг.дд.мм); даты текстом; разделяющие слова («серия хххх номер хххххх»).

### 3.3. Демаскирование
- Преобразование замаскированного текста в исходный с сохранением местоположения знаков.

### 3.4. Общие требования
- Подробное логирование на каждом этапе.
- Метрики: Latency, RPS, TPS (tokens per second).
- Ограниченный список систем, имеющих доступ к сервису.
- Гибкая настройка:
  - списка систем (вкл/откл доступа);
  - перечня типов ПД для идентификации/маскирования в зависимости от системы;
  - наличия демаскирования в зависимости от системы;
  - краткая инструкция по настройке (не более 5 предложений).

### 3.5. Реализация контракта API
- Эндпоинт `POST /process`.
- Запрос: `{ "payload": "<строка>", "payload_id": "<идентификатор>" }`.
- Ответ: `{ "result": "<строка>" }`.
- Логика: первый запрос с новым `payload_id` — маскирование (запомнить соответствие); второй запрос с тем же `payload_id` — демаскирование (вернуть исходную строку).
- Ответы: 200 (успех), 429 (перегрузка), 4XX (ошибка запроса), 5XX (внутренняя ошибка).

### 3.6. Дополнительные плюсы (необязательно)
- Токенизация/детокенизация либо замена синтетическими данными.
- Гибкая настройка вида маскирования/токенизации в зависимости от системы.
- RPS 2000 при Latency не более 1 секунды.
- Идентификация документов, удостоверяющих личность, кроме паспорта РФ.
- Маскирование только при наличии нескольких однозначно идентифицированных типов ПД (например, «пин-код карты» — не маскируем; «пин-код карты + номер карты» — маскируем); возможность изменения этих настроек.

## 4. Критерии (автоматическая проверка)

### 4.1. Проверка качества кода
- Загрузка решения в формате **zip** (только исходный код, без зависимостей/сборки/объёмных файлов).
- Без прохождения этой проверки решение **не учитывается**.

### 4.2. Нагрузочное тестирование
- Развёрнутое решение, реализующее контракт `POST /process`.
- Проверка по эталонному датасету, оценка точности маскирования и демаскирования и поведения под нагрузкой.
- **Прямая проверка (маскирование)**: исходная строка с новым `payload_id` → маска; сравнение с эталонной маской (метрика — нормированное span-based расстояние Левенштейна, [0..1]).
- **Обратная проверка (демаскирование)**: ваша маска с тем же `payload_id` → исходная строка; сравнение с исходной строкой из датасета.
- Проверяются категории ПД из ТЗ (ФИО, даты, паспорт, гражданство, орган выдачи, код подразделения, в/у, адрес, email, телефон, ИНН, номер карты, CVV, ПИН, имя держателя и сложные предложения).

### 4.3. Критерии успешного прохождения
- Реализован `POST /process` строго по контракту (`{payload, payload_id}` → `{result}`).
- Маскирование сохраняет соответствие по `payload_id`; повторный запрос с тем же id возвращает исходную строку.
- Ответ отдаётся быстро и стабильно под нагрузкой (RPS 1000+).
- Эндпоинт идемпотентен (безопасен к ретраям), корректно возвращает 429 при перегрузке.
- Сервис доступен по указанному URL (http или https) на момент прогона.
- Качество идентификации/маскирования/демаскирования — **не ниже 95%**.
- Latency — **не более 1 секунды**, RPS — **1000** (целевые значения).
