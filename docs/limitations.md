# Ограничения решения и план развития

## Ограничения

1. **RPS 2000 недостижим на одном процессе uvicorn на Windows.** Причина — GIL: детекция CPU-bound (regex), не масштабируется в потоках. Фактический потолок ~900-1000 RPS с серверной latency p95 ~2 мс. На Linux с несколькими воркерами RPS 2000 достижим.

2. **Vault в памяти одного процесса.** Соответствия `payload_id → {mask, original}` хранятся в in-memory LRU-кэше. При перезапуске процесса соответствия теряются. Для одного прогона проверки (~5 минут) достаточно, но не отказоустойчиво.

3. **Обработка 100 000 токенов занимает ~1.3 с.** В пределах таймаута проверяющей системы (10 с), но превышает целевой Latency 1 с для предельного случая. Для типовых запросов серверная latency p95 ~2 мс.

4. **Токенизация/детокенизация не реализована.** Это опциональный доп. плюс из ТЗ §6. Реализовано классическое маскирование/демаскирование.

5. **city/country/issuer не обобщаются на невиданные значения.** Детекторы построены на закрытых словарях городов/стран/органов выдачи. Города/страны вне словаря (например, «Березники», «Гвинея») не распознаются. fio обобщён (полное ФИО с невиданным именем маскируется).

6. **Короткое ФИО без ПД-контекста не маскируется.** «Иванов Иван» без контекста (клиент/гражданин/паспорт) не маскируется — осознанный компромисс: иначе замаскируется и «Пушкин Александр», нарушив ТЗ.

## План развития после хакатона

1. **Горизонтальное масштабирование**: общий vault через Redis, несколько воркеров uvicorn → RPS 2000+.
2. **Токенизация/детокенизация**: замена ПД на синтетические значения с сохранением смысла для LLM.
3. **Обобщение city/country/issuer**: морфологический/эвристический анализ вместо закрытых словарей.
4. **Интеграция с LLM**: встроенный прокси, который маскирует запрос, отправляет в LLM, демаскирует ответ.
5. **Мониторинг**: интеграция с Prometheus/Grafana, алерты на SLA.
6. **Шифрование vault**: шифрование соответствий в памяти и на диске.
